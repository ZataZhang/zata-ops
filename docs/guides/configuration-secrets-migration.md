# Nacos 与 OpenBao 生产配置迁移

本页用于把现有应用迁入独立的 Nacos 和 OpenBao，同时保留当前业务行为。示例采用部署平台读取 OpenBao、生成受限环境文件、应用启动时读取 Nacos 的方式；OpenBao Agent 渲染文件属于另一种接入方式，按实际消费者选择。

实例、服务账号、凭据引用和核验时间见私有清单。开始前按[部署后的登记与交付](private-secrets.md#deployment-handoff)确定材料落点。迁移期间保留可恢复路径，临时备份按用户约定保留或清理。

## 先确定加载顺序与变更范围

```text
可信发布流程 → OpenBao 应用读取身份 → 业务密钥与 Nacos 读取密码
    → 部署平台生成环境文件 → Compose 创建应用容器
    → 应用用专用账号读 Nacos → 装配有效配置 → 接收业务请求
```

把当前每个值归入以下三类，并确认同名值的覆盖顺序：

| 类别 | 存放位置 | 核对内容 |
| --- | --- | --- |
| 普通业务配置 | Nacos 的目标 namespace、group、Data ID | 值、类型、单位、结构化嵌套和空值语义 |
| 密码、API Key、签名密钥、带凭据的连接串 | OpenBao 的应用与环境专用 KV 路径 | 按当前消费者最终收到的原值迁移 |
| 发布与启动引导参数 | 部署平台或受限启动配置 | 服务地址、配置标识、域名、Compose 项目名和构建参数 |

应用已接收完整连接串时，可以将整串迁入 OpenBao。拆分字段、轮换密码、升级应用和改数据库结构分别评估，避免在一次配置迁移中同时改变这些行为。原有空字符串、未设置变量和默认值可能含义不同，核对时分别记录。

Nacos 和 OpenBao 的引导配置要能独立取得。Nacos 保存普通配置也可能包含内部拓扑，应继续使用鉴权和受控网络；不能因为未保存密码就视为可公开数据。

## 冻结基线，先发布再核对

修改私有记录前运行 `just private-backup`。通过可信子进程收集当前部署平台配置、实际容器环境、应用归一化后的有效设置、镜像标识、代码修订及必要部署文件，直接加密归档。`docker inspect`、展开后的 Compose 配置和应用设置对象都可能携带凭据，不输出到对话或普通日志。

在目标实例建立只读机器身份，按 namespace、group、Data ID 和 KV 路径验证授权。Nacos 普通配置和 OpenBao 密钥分别写入后，读回逐项比较；KV v2 更新用当前版本或 CAS 避免覆盖已有记录。比较程序仅输出通过状态、数量及必要的字段名。

预检使用当前生产镜像和预定的配置加载入口。只加载配置的临时容器不启动完整应用，不挂载生产数据卷，不注册正式路由。与基线比较所有有效字段，同时核对原始密钥，防止默认值掩盖注入失败。

## 核验环境文件与 Compose 转义

含 `$`、引号和反斜杠的密码会经过平台序列化、dotenv 解析和 Compose 插值。Compose 对未加引号和双引号值执行插值，单引号具有不同语义；不能用一种手工转义方式覆盖所有发布链路。[Docker 插值规则](https://docs.docker.com/compose/how-tos/environment-variables/variable-interpolation/)

Dokploy v0.31.0 的 `prepareEnvironmentVariablesForFile` 会处理反斜杠、引号和部分美元符号。该结论只适用于核对过的版本，升级后重新确认其生成逻辑。[版本化源码](https://github.com/Dokploy/dokploy/blob/v0.31.0/packages/server/src/utils/docker/utils.ts)

先用虚构且含特殊字符的值检查序列化规则，再沿实际 Compose 链路运行配置预检。`docker compose config --quiet` 只能检查配置是否可解析；展开后的展示文本也可能为了再次序列化而转义。以最终容器收到的值与应用解释结果为准，检查期间保持密钥正文不可见。平台生成的环境文件使用受限权限，按消费者需要设为 `0600` 或更严格。

## 固化网络并验证重建

手工 `docker network connect` 可用于定位问题，连接关系随后需要写回服务的 Compose 或实际发布定义。代理通过唯一服务名或网络别名访问上游；共享网络上避免使用会与其他实例冲突的通用别名。共享网络的服务接入、外部网络声明和生命周期按实际平台维护。[Compose 网络](https://docs.docker.com/reference/compose-file/networks/)

只把需要经过代理访问的服务接入共享入口网络。数据库仍保留在专用内部网络，核对宿主机绑定与发布端口，保持上游 TLS 证书校验。按已授权维护范围重建相关服务，验证网络别名、持久化数据和入口；未实际重建的共享代理如实记为未验证。

如 OpenBao token 绑定来源 CIDR，先从真正的发布进程测出口。经过反向代理时，同时核对 Traefik 入口白名单和 OpenBao 的 `x_forwarded_for_authorized_addrs`。受信任来源只覆盖受控代理；使用共享子网时，记录同网段其他容器处于该信任边界内。验证真实发布进程可读、非授权来源不可读，以及伪造 `X-Forwarded-For` 不会越过限制。[OpenBao TCP listener](https://openbao.org/docs/configuration/listener/tcp/)

## 在独立实例中演练恢复

备份至少覆盖 Nacos 数据库、必要的部署与鉴权配置、OpenBao Raft 快照及其解封材料引用。数据库恢复后按可行方式比较全部表数据；OpenBao 恢复后用原始解封材料解封，再用已登记身份读取目标路径并在内存中核对值。

恢复演练使用独立容器、命名卷和临时目录，限制外联；不连接生产数据卷。记录版本、seal 类型、Shamir 份额数和门限。在 OpenBao 2.7.2 的一次隔离恢复中，源实例为 3 份、门限 2，临时实例按 1 份、门限 1 初始化后解封失败；按源参数重建临时实例后恢复通过。这是该次演练的观察，其他版本和 seal 方式应核对对应流程。

`snapshot-force` 会绕过快照密钥一致性检查，不能代替原始解封材料。需要使用时只针对已确认可丢弃的恢复目标执行；恢复生产实例另行确认目标和影响。完成后移除演练容器、卷及明文暂存文件。[Raft 快照 API](https://openbao.org/docs/api/system/storage/raft/)，[封存与解封](https://openbao.org/docs/concepts/seal/)

## 经真实发布入口切换

先确认生产容器、代码修订和部署平台配置仍与基线一致，且没有另一项发布正在执行。仅把已验证的新连接参数与密钥引用写入目标应用，保留引导参数、构建参数和原有覆盖关系。

Dokploy v0.31.0 中，`deployCompose` 含代码克隆步骤，`rebuildCompose` 使用现有部署目录。仅迁移配置且需要保留已核对代码时，核实当前版本的 redeploy/rebuild 路径；部署命令仍可能构建镜像，不能据此承诺镜像标识不变。不要借配置迁移拉取未经核对的新代码，也不清空卷。[版本化实现](https://github.com/Dokploy/dokploy/blob/v0.31.0/packages/server/src/services/compose.ts)

切换后通过实际发布进程和实际应用容器检查：

- 发布平台确实读取了目标 OpenBao 路径，应用确实使用新 Nacos 地址与配置标识。
- 运行中容器的密钥值、有效应用设置及结构化配置与基线一致。
- HTTPS 前台、管理端和后端健康入口可用，预期未变更的环境状态正常。
- 真实账号能够登录，并通过应用入口完成一次代表性的业务调用；健康检查只覆盖它实际探测的范围。

失败时依据保留的发布配置恢复原引用，并验证真实业务入口；不要先删除源配置或回滚材料。相关验收规则见[测试标准](../ai-standards/testing.md)。

## 登记生命周期，按约定收尾

人用登录会话、应用发布身份和应急恢复材料分别登记。个人 Userpass token 的会话 TTL 不等于账号密码的有效期；AppRole 的 SecretID 有效期、使用次数与签发 token 的寿命也分别维护。具体取用和轮换方式见[OpenBao 日常使用指南](openbao-usage.md)。

静态 Provider token 登记精确到期时间、权限、来源限制和换新责任。轮换顺序为签发新 token、更新 Provider 和私有凭据记录、通过真实发布进程验证读取、再撤销旧 token。已登记到期时间不代表已经有自动提醒或自动轮换。对于发布时注入密钥的应用，Provider token 到期会影响后续读取；应用已经取得的外部凭据不会因此自动失效。

按[私有备份恢复指南](private-inventory.md#private-config-restore)核对当前运维配置可恢复。分别记录本机加密归档、异机副本、独立恢复私钥的实际状态；用户选择本机临时备份时沿用其选择，并记录电脑丢失后的恢复缺口。

确认迁移验证完成后，按用户约定清理临时回滚快照和演练资源，核对它们是否曾被嵌套打包进其他归档。清理范围不包含日常登录凭据、初始化解封材料、必要的当前配置备份和非敏感验证记录。共享历史归档如含临时副本，处理时保留其他成员内容，并验证新归档可解密。

通用执行规则维护在 skill，操作步骤维护在本指南；真实实例状态维护在 `config/private/`，对外复盘仅使用脱敏示例，避免将历史案例当作当前线上事实。
