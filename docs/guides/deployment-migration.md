# 自动部署迁移与后台任务排空

本页是运维流程，复用已有 SSH、清单、凭据和现场检查入口；当前没有通用的
`deploy migrate` 或 Celery 排空命令。具体服务发布脚本仍由业务仓库维护。
真实服务器、部署用户、密钥引用、GitHub environment 与验收记录保存在私有清单和快照中。

## 迁移前确认实际发布版本

先读取业务仓库的 AGENTS.md、部署文档、workflow 和发布脚本，区分 main push、tag 和手动运行
分别指向哪个环境。核对远程 main 的已知修复是否包含在候选提交中；本地分支存在或测试通过
都不能证明实际镜像包含这些修复。生产构建应有明确源码提交，记录镜像引用和摘要；
如有本地覆盖文件，必须逐项记录，不能把基线 SHA 当作完整源码版本。

只读核对命令示例（remote 名按业务仓库实际配置）：

```bash
git fetch origin
git status --short --branch
git log --oneline HEAD..origin/main
git rev-parse HEAD
```

同时核对现有生产的域名、证书、容器布局、资源上限、挂载、运行 UID、远程数据库与缓存。
不要仅替换 SSH IP 后直接套用旧栈，更不能把单机部署变成额外创建一套数据库、Redis 或主站。

## 部署身份与配置边界

每个应用可采用 `<app>-deploy` 专用用户和独立 SSH 密钥，保留管理员现有登录方式。
通过已有可信连接核对主机公钥，GitHub 保存经过验证的 known_hosts，并启用严格主机校验。
不要扫描后直接信任主机密钥。非 22 端口使用 `[host]:port` 格式。
部署用户需能写发布目录、读启动配置并拉取镜像；Docker 组权限接近 root，不等于严格隔离，
通常无需再授予通用免密 sudo。

GitHub environment 保存目标地址、用户、路径、健康入口及 SSH Secret。
业务密钥留在服务器受保护的启动文件或配置中心；Nacos 使用应用只读账号。
本地和容器同名环境变量可能覆盖 Nacos，应核对遗留覆盖项。
dotenv 应由解析器读取且保留字面值，不要对配置中心返回的任意正文执行 shell `source`。
通过 [Nacos dotenv 安全使用](nacos-env.md) 的入口只列键或注入可信命令，不回显配置正文。

## 镜像与发布串行

测试和生产若共用 registry / namespace，镜像引用必须隔离构建配置，例如
`<commit SHA>-staging` 与 `<commit SHA>-production`；只用 SHA 可能让不同环境的前端构建互相覆盖。
构建任务读取对应 GitHub environment 的变量，回滚记录完整镜像标签或摘要。
前端构建 Secret 可通过 BuildKit secret 注入，避免进入 Docker ARG / ENV 层；
最终打包进浏览器的值仍是客户端可见配置。

同一生产目标的发布应串行，不能按 ref 分锁，也不能取消正在执行的发布来切换版本。
远程发布锁还需覆盖手工发布入口；多个入口必须使用同一把锁才有保护作用。

## 有计费或长时间任务的服务

队列为空、Redis unacked 为空或容器 healthy，都不能证明 Worker 没有正在执行的任务。
按业务项目的任务系统执行：

1. 记录现有消费队列，暂停领取新任务；保留排队消息，不 purge 队列。
2. 检查 active、reserved、scheduled，等待已领取任务完成。
3. Worker 无响应、状态不完整或等待超时时终止发布，恢复原有消费。
4. 排空后更新服务，校验实际镜像、容器健康及真实 HTTP 入口。
5. 成功后再切换 current 指针，并恢复消费。
6. 回滚前也必须检查并排空新 Worker 已领取的任务，不能再次强停在途任务。

停止宽限期只是退出缓冲，不能替代排空。早确认的任务被强杀后可能留下业务 PROCESSING、
Celery PENDING 的孤立记录；不要据此直接重放整个任务。先核对业务记录和上游任务，
上游已完成时优先取回原结果，按原业务模式持久化，避免重复提交、扣费或错误退款。

即使最终文件存储在 OSS，处理链路仍可能需要可写的临时目录；按容器运行 UID 验证真实写入。
本地权限错误应快速失败，网络请求应设置连接和读取超时，退避等待要有上限。

## 验收与记录

分别记录 SSH、私有镜像拉取、配置解析、暂停/排空/恢复、健康入口及 GitHub 运行结果。
完整预演可验证部署链路而不替换生产镜像；不能把预演写成新版本已经上线或生产回滚已经实测。
只对有独立生产授权的实际发布执行版本切换。

修改已有私有资料前先 `just private-backup`，将验证时间、实际运行版本、候选版本、
workflow URL、部署用户和密钥引用写入私有快照，随后执行清单格式化与校验。
关闭旧服务的时点以新入口验证和业务任务状态为依据；保留回退所需数据，检查旧流水线不会重新拉起服务。
