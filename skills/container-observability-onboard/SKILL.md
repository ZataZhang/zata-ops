# 应用容器接入日志与指标平台

将目标应用接入用户已有平台，保持应用部署和采集器生命周期分离。使用中文说明，不写入真实服务器地址、项目名称或凭据作为模板默认值。

## 先确定接入范围

1. 读取目标仓库的 `AGENTS.md` 和按任务要求路由到的规范。
2. 区分用户要接入的是容器日志、主机指标还是应用指标，不把三者当成自动同时具备。
3. 检查目标服务器是否已有采集器，以及它的配置、采集范围和 Compose 项目名。同机新增服务优先复用现有采集器，避免重复采集；新服务器通常部署独立采集器。
4. 确认中心平台地址、日志写入和指标写入契约、认证方式及凭据来源。Grafana 浏览地址不一定是写入地址，不能据此推导未经确认的接收端。
5. 只读确认容器输出、磁盘、可用内存、Docker 日志驱动和轮转策略；不要打印完整业务日志或 `.env` 来确认配置。

只有查看或解释权限时不执行部署。接入权限不包含新建中心平台、开放管理端口、修改业务密钥或重新发布应用。缺少中心平台或需要额外的网络权限时，说明所缺条件并请求方向。

## 复用资产

若用户的环境可访问 zata-ops 源码，定位该仓库并检查现有 `deploy/monitoring/collector.compose.yml`、`collector.env.example` 和 `vector/vector.yaml`；以实际内容为准，不假定安装后的 skill 相对目录仍包含这些文件。

优先复用同一份采集配置，通过环境变量区分服务器和接收端，不复制一份配置给每个应用。没有源码资产时，按 [接入契约与验证](references/onboarding.md) 生成目标项目需要的最小配置，并核验所选采集器版本的官方说明，不凭记忆沿用版本相关参数。

## 按接入类型实施

- **日志**：检查应用是否输出到 stdout/stderr；普通文本可采集，JSON 便于结构化查询，但不是接入前提。只写文件时，需要明确文件挂载和采集权限，或经授权调整应用输出，不能宣称 Docker 日志采集已覆盖文件日志。
- **主机指标**：按需启用 Vector host metrics 或复用已有 exporter。核对容器中的 `/proc`、`/sys`、文件系统路径和网络命名空间，避免把采集器自身资源当成宿主机资源。
- **应用指标**：确认真实 `/metrics` 接口、认证、可达路径和指标名称后再配置 scrape/remote write。只采集主机指标不能交付为请求量、错误率或接口延迟已接入。

## 配置与操作边界

- 默认交付采集器 Compose、共用采集配置、安全的 env 示例及验证方法。若多条部署命令反复执行，再提供幂等接入脚本和只读检查入口；不要另建不必要的采集框架。
- 为服务器设置唯一且稳定的 `NODE_NAME`，日志附加项目、服务标签；不要把请求 ID、用户 ID 或完整 URL 用作 Loki 标签。应用 JSON 不应覆盖可信 Docker 元数据。
- 使用专用写入凭据，不使用 Grafana 管理员密码。新增身份应追加并保留已有用户；不要为新服务器重跑会覆盖中心认证用户文件的初始化脚本。
- 凭据以标准输入或受限文件传输，不出现在命令参数、日志、镜像或 Git 中。本地/远端 env 权限应受限，真实配置被 Git 忽略；已有配置更新前备份。
- 跨服务器使用校验证书的 HTTPS 或已有可信私网通道。遇到连接失败，分层检查 DNS、端口、云安全组、主机防火墙、TLS、认证与路由，不用跳过证书校验解决问题。
- Docker socket 只读挂载不代表只读 API 权限；采集器属于高权限可信组件。按用户范围限制采集目标，并明确日志可能包含敏感信息；不默认将所有业务日志发送到新第三方服务。
- 采集器使用独立目录、Compose 项目名、资源限制、缓冲和自身日志轮转；部署或回退仅针对采集器，不重启业务容器、不清理业务数据卷，也不承诺补采全部历史日志。
- 远端配置先校验再启动；更改本地文件不等于远端已生效。跨平台打包时排除 macOS `._` 附带文件，避免被当成配置加载。

## 验证与交付

实施或排查时读取 [接入契约与验证](references/onboarding.md)，完成配置验证、安全负向测试及真实数据测试。

交付应说明：已接入哪些服务器/服务、日志查询方法、已验证的指标、凭据保存位置及未覆盖范围。分别报告“采集器运行”“写入成功”“查询成功”，不把容器 Up 当作接入完成。不自动 commit、push 或操作中心平台，除非用户另有授权。
